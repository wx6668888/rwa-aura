# 质押与提现流程及逻辑检查

本文档梳理用户从**质押**到**提现**的前后端操作与分支逻辑，并标注不合理或潜在问题。

---

## 一、质押流程

### 1.1 前端：质押入口与校验

| 步骤 | 位置 | 行为 |
|------|------|------|
| 选择模式 | `stake-action-panel.tsx` | 二选一：USDT 质押 / RWA 质押 |
| 金额 | 同上 | USDT 最少 100；RWA 按 1 RWA≈0.85 USDT 折算，最少约 117.65 RWA |
| 推荐人 | 同上 | 首次必填且不能为自己；已有推荐人则用链上绑定，不再填 |
| 锁仓 | 同上 | flexible / 30 / 90 / 180 / 365 天 |
| 授权 | useUSDT / useRWA | approve 对应 token 给 StakingContract |
| 调用 | useStakingContract | USDT: `stake(amount, referrer, lockPeriod)`；RWA: `stakeRWA(amount, referrer, lockPeriod)` |

- **金额精度**：前端 `stake(amount)` 传字符串，hook 内用 `parseUnits(amount, 6)`（USDT）或 `parseUnits(amount, 18)`（RWA），与合约一致。
- **推荐人**：已有推荐人时传 `0x0`，合约 `_bindUnifiedReferrer` 会保留已绑定推荐人，逻辑正确。

### 1.2 合约：StakingContract

**USDT 质押 `stake()`**

- 要求 `amount >= 100 * 10^6`（100 USDT）。
- 50% 转国库、50% 留合约；若配置了 stRWA 则给用户 mint 国库对应部分的 stRWA。
- 更新 `users[user]`（totalStaked、firstStakeTime、referrer 等）、`usdtLockedPrincipals` 或 `usdtFlexiblePrincipal`，写 `stakeLockPeriods[stakeId]`，发 `StakeEvent`。

**RWA 质押 `stakeRWA()`**

- 无最小金额（仅前端有 100 USDT 等值校验）。
- 50% 转国库、50% 留合约；若配置 stRWA 则 mint 对应 stRWA。
- 更新 `rwaStakes[user]`、`rwaLockedPrincipals` 或 `rwaFlexiblePrincipal`，发 `RWAStakeEvent`。

**潜在不一致**：合约侧 RWA 无最小质押额，前端用 0.85 折算 100 USDT 等价。若 RWA 价格配置或展示不一致，可能出现“前端不让质押、合约允许”或反过来，建议在文档或 UI 明确“最小 100 USDT 等值”。

### 1.3 后端：EventMonitor

- 轮询链上事件（含 12 块确认延迟），处理 `StakeEvent`、`RWAStakeEvent`。
- **升级仅计锁仓**：`cumulative_personal_stake` 与团队量（`updateTeamVolume`）仅在 **lockPeriod > 0** 时累加，无锁仓（灵活）不纳入节点等级考核。
- **StakeEvent**：写 `stakes`；`total_staked` 始终累加，`cumulative_personal_stake` 仅当 lockPeriod>0 累加；绑定推荐关系；`triggerRewardCalculation(..., isLocked)`，仅 isLocked 时更新团队量。
- **RWAStakeEvent**：同上，仅锁仓时累加 cumulative 与团队量；RWA 团队量按 0.85 换算为 USDT 等值写入。

### 1.4 后端：RewardEngine.processStake

- 入参：`(userAddress, stakeAmount, stakeId, assetType)`，**assetType 区分 USDT / RWA**（EventMonitor 在 StakeEvent 传 'USDT'，RWAStakeEvent 传 'RWA'）。
- 用 `referral_relations` 算上级的级差奖励，得到 `RewardDistribution[]`。
- 写 DB `rewards`，再按 assetType 调用合约：**USDT** 时 `updateUserRewards(beneficiary, 0, reward.amount, stakeId)`；**RWA** 时 `updateUserRewards(beneficiary, reward.amount, 0, stakeId)`，推荐人奖励正确进入对应池。

**问题 1（严重）**：  
- 合约 `updateUserRewards(user, rwAmount, usdtAmount, stakeId)` 约定：**usdtAmount==0** 时更新 `rwaStakes[user].rwaPending`（RWA 奖励），**usdtAmount!=0** 时更新 `users[user].rwaPending` 与 `users[user].usdtRewards`（USDT 质押的 RWA+USDT 奖励）。
- 当前后端对 **RWA 质押** 仍传 `(beneficiary, '0', reward.amount, stakeId)`，即把 RWA 金额当成了 usdtAmount，导致：
  - 推荐人本应增加的 **RWA 待领取** 被加到了 **USDT 侧的 rwaPending/usdtRewards**，或触发合约校验/失败。
- **建议**：EventMonitor 在触发奖励计算时传入资产类型（如 `assetType: 'USDT' | 'RWA'`）；RewardEngine.processStake 根据类型调用合约：  
  - USDT 质押：`updateUserRewards(beneficiary, 0, reward.amount, stakeId)`；  
  - RWA 质押：`updateUserRewards(beneficiary, reward.amount, 0, stakeId)`。

## 二、提现流程

### 2.1 提现类型概览

| 类型 | 合约方法 | 前端入口 | 说明 |
|------|----------|----------|------|
| USDT 质押的 RWA 奖励 | `withdraw(amount, chooseStRWA)` | RwaWithdrawCard | 扣 24h 冷却；≥100；选即时到账(8% 费)或 120% stRWA 锁 30 天 |
| RWA 质押的 RWA 奖励 | `withdrawRWARewards(amount, chooseStRWA)` | RwaWithdrawCard | 同上，独立冷却与余额 |
| 灵活 USDT 本金 | `withdrawFlexibleUSDTPrincipal()` | PrincipalWithdrawActions | 全额灵活 USDT 一次提完，扣 8% 等 |
| 灵活 RWA 本金 | `withdrawFlexibleRWAPrincipal()` | PrincipalWithdrawActions | 全额灵活 RWA 一次提完，扣 8% 等 |
| 到期 USDT 锁仓本金 | `withdrawUSDTPrincipal(lockIndex)` | PrincipalWithdrawActions | 到期后按 lockIndex 提 principal |
| 到期 RWA 锁仓本金 | `withdrawRWALockedPrincipal(lockIndex, chooseStRWA)` | PrincipalWithdrawActions | 到期后可选即时(8%)或 120% stRWA 锁 30 天 |
| 紧急退出（USDT 锁仓） | `emergencyWithdraw(lockIndex)` | 应急/紧急页面 | 未到期按已过天数比例退本金，再扣 8% |

### 2.2 RWA 奖励提现（RwaWithdrawCard）

- 展示“可用 RWA”= 链上 `userStakeInfo.rwaPending`（USDT 质押收益）+ `rwaStakeInfo.rwaPending`（RWA 质押收益）。
- 用户输入 `numAmount` 后分支：
  1. `numAmount <= usdtRwaPendingNum` → 只提 USDT 侧：`withdraw(amount, chooseStRWA)`。
  2. `numAmount > usdtRwaPendingNum` 且 `numAmount <= rwaStakeRwaPendingNum` → 只提 RWA 侧：`withdrawRWARewards(amount, chooseStRWA)`。
  3. `numAmount > usdtRwaPendingNum` 且 `numAmount <= rewardsTotalNum`（跨两池）→ 先 `withdraw(usdtPart, chooseStRWA)`，再 `withdrawRWARewards(rwaPart, chooseStRWA)`。

**问题 2（体验/一致性）**：  
- 分支 2 会“全部从 RWA 池扣”，即当 USDT 池有 50、RWA 池有 80、用户填 60 时，会从 RWA 池提 60，USDT 池 50 不动。若产品希望“优先消耗 USDT 池”或“按比例两池各提”，需改逻辑或加说明。
- 分支 3 两笔交易：若第一笔成功、第二笔失败，会出现“只提了 USDT 部分”的状态；且目前只把第二笔的 `hash` 给 overlay，第一笔 hash 未展示。建议：两笔都展示或明确提示“将发起两笔交易”。

**问题 3（精度）**：  
- `usdtPart = usdtRwaPendingNum.toFixed(6)`、`rwaPart = (numAmount - usdtRwaPendingNum).toFixed(6)` 用 6 位小数；合约为 18 位。一般不会出错，但若将来合约或 UI 用更高精度，建议统一用 18 位或合约要求的精度。

### 2.3 本金提现（PrincipalWithdrawActions）

- 灵活本金：从 `useStakingContract` 读 `usdtFlexiblePrincipal` / `rwaFlexiblePrincipal`（实际来自合约的 flexibleTotalStaked），≥100 才显示按钮并允许提。
- 锁仓本金：从 `usdtLockedPrincipals` / `rwaLockedPrincipals` 取 `canWithdraw && !withdrawn && amount >= 100` 的项展示，到期后按 index 调 `withdrawUSDTPrincipal(index)` 或 `withdrawRWALockedPrincipal(index, chooseStRWA)`。
- 逻辑与合约一致；合约侧最小提现 100（18 位）与前端 MIN_WITHDRAW=100 一致。

### 2.4 合约提现逻辑要点

- **withdraw / withdrawRWARewards**：扣减对应 `rwaPending`、更新 `lastWithdrawTime`，满足 24h 冷却和最小 100（18 位）；chooseStRWA 时 mint 120% 锁 30 天 stRWA，否则走 `_payoutRwaImmediate`（8% 费用拆分：buyback/treasury/pool）。
- **灵活/锁仓本金**：扣减对应 principal 与 totalStaked，再调 `_payoutUsdtImmediate` 或 `_payoutRwaImmediate`（同样 8% 拆分）。
- **emergencyWithdraw**：仅 USDT 锁仓、未到期；按已过整天数比例算可退本金，再扣 8% 即时到账。

### 2.5 后端对提现事件的反应

- EventMonitor 监听 `WithdrawalRequested`、`RWARewardWithdrawn`、`FlexibleUSDTPrincipalWithdrawn`、`USDTPrincipalWithdrawn`、`FlexibleRWAPrincipalWithdrawn`、`RWAPrincipalWithdrawn`、`EmergencyWithdrawal`。
- 处理方式：按 user 调用 `syncUserState` / `syncRWAStakeState`，用合约当前 `users(user)`、`rwaStakes(user)` 覆盖 DB 中对应用户状态，保证后端视图与链上一致。逻辑合理。

### 2.5.1 如何计算用户的「总留存」— 公式与所有情况

- **公式**：对任意用户，其 **总留存** = **团队总充值（USDT 等值）** − **团队总提现（USDT 等值）**。  
  其中「团队」= 该用户本人 + 其全部下级（推荐关系树中的所有人）。  
  后端用 `users.team_total_deposited`、`users.team_total_withdrawn` 存每个用户的团队累计充值/提现，总留存 = 两数相减（若为负则视作 0）。

- **计入「充值」的所有情况**（任一笔都会给该用户 + 其所有上级的 `team_total_deposited` 加上对应 USDT 等值）：

| 序号 | 场景 | 触发事件 | 计入金额（USDT 等值） |
|------|------|----------|------------------------|
| 1 | 用户质押 USDT | StakeEvent | amount（合约内部 18 位，即 USDT 金额） |
| 2 | 用户质押 RWA | RWAStakeEvent | amount × 0.85（RWA 按 0.85 折 USDT） |

说明：充值不区分有无锁仓，**有锁仓、无锁仓的质押都会**增加团队总充值。

- **计入「提现」的所有情况**（任一笔都会给该用户 + 其所有上级的 `team_total_withdrawn` 加上对应 USDT 等值；一律按 **gross**，即扣费前金额，例如提 100、手续费 8%、到账 92 仍按 100 计）：

| 序号 | 场景 | 触发事件 | 事件中的金额 | 计入提现的 USDT 等值 |
|------|------|----------|--------------|----------------------|
| 1 | USDT 质押的 RWA 奖励提现（即时 RWA 或选 stRWA） | WithdrawalRequested | amount = 扣减池子的 RWA 数量（gross） | amount × 0.85 |
| 2 | RWA 质押的 RWA 奖励提现（即时 RWA 或选 stRWA） | RWARewardWithdrawn | amount = 扣减池子的 RWA 数量（gross） | amount × 0.85 |
| 3 | 灵活 USDT 本金提现 | FlexibleUSDTPrincipalWithdrawn | grossAmount, netAmount | grossAmount（已是 USDT gross） |
| 4 | 到期 USDT 锁仓本金提现 | USDTPrincipalWithdrawn | grossAmount, netAmount | grossAmount（已是 USDT gross） |
| 5 | 灵活 RWA 本金提现 | FlexibleRWAPrincipalWithdrawn | amount = netAmount（RWA 净额） | (amount / 0.92) × 0.85（先还原 gross 再折 USDT） |
| 6 | 到期 RWA 锁仓本金提现（选 RWA 或选 stRWA） | RWAPrincipalWithdrawn | amount（选 RWA 时为 net，选 stRWA 时为 1.2×本金） | (amount / 0.92) × 0.85（统一按 gross 处理；选 stRWA 时会略高估） |
| 7 | 紧急退出（USDT 锁仓未到期按比例退） | EmergencyWithdrawal | refundAmount = net（用户实收 USDT） | refundAmount / 0.92（还原为 gross） |

- **汇总**：  
  - 充值：2 种（USDT 质押、RWA 质押），金额均为 USDT 等值（RWA×0.85）。  
  - 提现：7 种（上表 1～7），金额均按 **gross** 折成 USDT 等值后累加。  
  - 用户 A 的「总留存」= A 的 team_total_deposited − A 的 team_total_withdrawn（且 ≥ 0）。

- **为何会显示 0/2000？**  
  后端用 `users.team_total_deposited` 与 `users.team_total_withdrawn` 存团队总充值、总提现；这两列只有在 **EventMonitor 处理到质押/提现事件时** 才会累加。若用户的质押、提现发生在「总留存」功能上线之前，当时没有写入这两列，因此会一直是 0，总留存也就显示为 0。  
  **解决办法**：对历史数据做一次回填。运行 `scripts/backfill-team-retained.ts`（会按 `stakes` 表补算 team_total_deposited，按 `withdrawal_log` 补算 team_total_withdrawn）。  
  查询某用户的总充值/总提现/总留存：运行 `scripts/query-user-retained.ts <地址>`，或调用接口 `GET /api/user/:address/level-info`（返回里含 `teamTotalDeposited`、`teamTotalWithdrawn`、`teamRetained`）。

### 2.6 总留存：提现金额按 gross（扣费前）计

- **总留存定义**：团队所有充值金额 − 团队所有提现金额（以 USDT 计，RWA 按 0.85 折算）。
- **提现按多少算**：一律按 **gross（扣费前、从池子划出的金额）** 计入。例如：用户提现 100、手续费 8%、实际到账 92，**仍按 100 计提现**，不按 92。
  - USDT 本金：合约传 `grossAmount`，直接使用。
  - USDT 奖励 / RWA 奖励：事件里的 `amount` 即为扣减池子的金额（gross），直接使用（RWA 再×0.85 折 USDT）。
  - RWA 灵活本金：事件只有 net，后端用 `gross = net/0.92` 再×0.85 折 USDT。
  - RWA 锁仓本金（选 RWA 或选 stRWA）：事件里 amount 可能为 net 或 stRWA 面额，后端统一按 `gross = amount/0.92` 再×0.85 折 USDT，保证“选 RWA”时按 100 计；选 stRWA 时会略高估，可接受。
  - 紧急退出：事件为 net，用 `net/0.92` 作为 gross 计入。
- 不单独监听 `StRWAMinted`，避免与 `RWAPrincipalWithdrawn` 同笔重复记账。

### 2.7 用户「提取 stRWA」的设计（获得与使用 stRWA）

- **stRWA 是什么**：StRWA 是 ERC20 凭证，1 stRWA = 1 USDT 等值实体资产；仅 StakingContract 可铸造/销毁，可在二级市场持有或通过 SwapContract 换回 RWA。
- **用户如何获得 stRWA（选“提取 stRWA”）**  
  在以下两处，用户可选择「要 RWA 即时到账（8% 手续费）」或「要 stRWA（无手续费、多拿 20%）」：
  1. **RWA 奖励提现**（`withdraw` / `withdrawRWARewards`）：选 `chooseStRWA = true` → 不扣 8%，改为铸造 **120% 对应金额的 stRWA** 给用户，**锁 30 天**（`_mintStRWA(..., ST_RWA_LOCK_DURATION)`）。
  2. **RWA 锁仓本金到期**（`withdrawRWALockedPrincipal(lockIndex, chooseStRWA)`）：选 `true` → 不扣 8%，同样获得 **120% 本金的 stRWA**，锁 30 天。
- **锁定期**：上述方式获得的 stRWA 通过 StRWA 合约的 `mintLocked` 铸造，锁 30 天内不可转账；到期后自动变为可用余额（`availableBalanceOf`），可转账或参与互换。
- **用户拿到 stRWA 之后怎么“提取/变现”**  
  - **未锁部分**：可直接 ERC20 转账给他人，或到 **SwapContract** 调用 `swapStRWAToRWA(stRwaAmount)`，把 stRWA 转给合约、按 AMM 池子换出 **RWA**（无税）。  
  - StRWA 合约注释中的「用户解锁 stRWA」「用户互换 stRWA → RWA」：当前实现里「互换」在 SwapContract 完成（用户转 stRWA 进池、池子转 RWA 给用户），StakingContract 未提供单独的 burn/redeem 接口；锁到期后只是余额变为可用，不涉及 StakingContract 的 burn。
- **总留存对“选 stRWA”的计入**：用户选「要 stRWA」时，仍会触发 `WithdrawalRequested` / `RWARewardWithdrawn` / `RWAPrincipalWithdrawn`，后端按 **gross（100%）** 计入团队提现（选 RWA 时用 net/0.92 还原 gross；选 stRWA 时事件里 amount 为 120% 本金或奖励，统一按 gross 规则处理，见 2.6）。

## 三、其他发现

### 3.1 重复的 refetchStakeInfo

- `stake-action-panel.tsx` 里有两个 `useEffect` 都在 `[isConnected, address, refetchStakeInfo]` 时调用 `refetchStakeInfo()`，可合并为一个，避免重复请求。

### 3.2 成功后的跳转与 hash 展示

- 质押成功后会跳 dashboard，且交易链接写死 `https://bscscan.com/tx/${txHash}`。在 BSC 测试网或本地链上应使用当前链的区块浏览器（如 testnet.bscscan.com 或 chainId 配置），否则链接错误。

### 3.3 前端“可提 RWA”与合约一致性

- 前端“可提 RWA”= 两池 rwaPending 之和，与合约两个独立池一致；用户跨池提现时由前端拆成两笔调用，逻辑正确。唯一要注意的是上面提到的“两笔时只展示一个 hash”和“第一笔成功、第二笔失败”的提示。

### 3.4 最小提现 100 的展示

- 合约 MIN_WITHDRAWAL_AMOUNT = 100 * 10^18（100 个 18 位精度的 token）；前端 MIN_WITHDRAW = 100，数字一致。若产品文档或 UI 写“最小 100 USDT/RWA”，需明确是“100 个 token 单位”而非 100 美元等值。

## 五、流程图（简要）

```
用户质押
  → 前端：授权 + stake / stakeRWA
  → 合约：StakeEvent / RWAStakeEvent
  → 后端 EventMonitor：入库 + triggerRewardCalculation
  → RewardEngine.processStake：级差计算 + updateUserRewards（按 assetType 区分 rwAmount/usdtAmount，已修复）

用户提现 RWA 奖励
  → RwaWithdrawCard：根据金额选 withdraw / withdrawRWARewards / 两笔
  → 合约：扣 rwaPending、24h 冷却、选 stRWA 或即时 8% 费
  → 后端：监听事件 → syncUserState / syncRWAStakeState

用户提现本金
  → PrincipalWithdrawActions：灵活/锁仓 → 对应 withdrawFlexible* / withdraw*Principal
  → 合约：扣 principal、扣 totalStaked、8% 费或 stRWA
  → 后端：同上 sync
```

如需对某一处做具体代码级修改（例如 RewardEngine 区分 USDT/RWA 调用合约），可以指定文件与函数名继续改。
