# RWA 协议项目逻辑与用户层审查报告

> 审查范围：合约、后端、前端的完整用户流程；重点关注漏洞、不合理与用户侧风险。  
> 日期：2026-03-05

---

## 一、项目整体逻辑概览

### 1.1 核心流程

| 环节 | 链上 (StakingContract) | 后端 | 前端 |
|------|------------------------|------|------|
| **质押 USDT** | `stake(amount, referrer, lockPeriod)`，50% 国库 / 50% 合约，可绑推荐人（仅首次） | EventMonitor 监听 StakeEvent → 写 stakes/users → bindReferralRelationship → 触发 RewardEngine | 输入金额/推荐人/锁仓期 → Approve → stake |
| **质押 RWA** | `stakeRWA(amount, referrer, lockPeriod)`，50% 国库 / 50% 合约或灵活本金 | 监听 RWAStakeEvent → 写 stakes/rwa_stakes/rwa_locked_principals → bindReferralRelationship → 触发奖励 | 同上，模式切换 RWA |
| **推荐奖励** | 由后端调用 `updateUserRewards(user, rwAmount, usdtAmount, stakeId)` 写入链上 | RewardEngine 按 referral_relations 算各级奖励 → 写 DB → 调合约 | 提现页领取 USDT |
| **RWA 收益提现** | `withdraw(amount, chooseStRWA)` 提 UserInfo.rwaPending（USDT 质押产生的 RWA） | - | 提现卡：选提 U / 持 RWA，扣 5% 费 + 24h 冷却 |
| **RWA 本金/灵活** | `withdrawFlexibleRWAPrincipal()`、`withdrawRWAPrincipal(lockIndex)` | - | 同一张提现卡合并展示与操作 |

### 1.2 数据流要点

- **推荐关系**：链上 `UserInfo.referrer`（USDT 用户）与 `RWAStakeInfo.referrer`（RWA 用户）**各自独立**，可理论上有两个不同推荐人。
- **后端推荐数据**：仅维护 `users.referrer` 和 `referral_relations`，**只认“第一次”绑定的推荐人**，与链上可能不一致。
- **奖励发放**：RewardEngine 完全按 DB 的 `referral_relations` 算奖并调合约，不读链上 referrer。

## 二、漏洞与严重问题

### 2.1 【高】推荐人链上与 DB 不一致，导致奖励发错人

**现象**：  
链上允许同一地址在 **USDT 质押** 和 **RWA 质押** 时各绑一次推荐人（`UserInfo.referrer` 与 `RWAStakeInfo.referrer` 可不同）。后端只在 **第一次** 写入 `users.referrer` 并构建 `referral_relations`，之后不再更新。

**后果**：  
- 若用户先 RWA 质押绑 A、后 USDT 质押绑 B，链上 USDT 的 referrer 是 B，但 DB 和奖励仍按 A 发。
- 或先 USDT 绑 B、后 RWA 绑 A，则 RWA 相关奖励会发给 B 而非 A。

**建议**：  
- **方案 A**：合约统一为“一人一个推荐人”，例如在绑定 USDT 推荐人时同步写入 RWA 的 referrer（若尚未绑定），避免同一用户链上出现两个推荐人。  
- **方案 B**：后端按 **当前这笔质押事件** 的 referrer 来算奖并更新/重建该用户的推荐链（例如按事件来源区分 USDT/RWA），而不是只认第一次。

---

### 2.2 【高】RWA 质押收益可能无法提现（合约与前端不一致）

**现象**：  
- 合约中仅有 `withdraw(amount, chooseStRWA)`，操作的是 **UserInfo.rwaPending**（USDT 质押产生的 RWA 收益）。  
- **RWA 质押** 产生的收益在 **RWAStakeInfo.rwaPending**（`updateUserRewards` 中 `usdtAmount==0` 时写入），但当前 **StakingContract.sol 内未发现 `withdrawRWARewards`** 等从 `rwaStakes[msg.sender].rwaPending` 提现的函数。

**后果**：  
若部署的合约与当前仓库一致，则 RWA 质押产生的 RWA 收益**无法在链上提现**；前端却调用 `withdrawRWARewards`，会导致调用失败或依赖未部署的接口。

**建议**：  
- 若主网/测试网合约已包含 `withdrawRWARewards`，请将合约代码与仓库同步，避免后续维护脱节。  
- 若当前合约确实没有该函数，应在合约中新增：从 `rwaStakes[msg.sender].rwaPending` 扣减、应用与 USDT 收益提现相同的 5% 费与 24h 冷却，再转出 RWA 或按 chooseStRWA 转 stRWA。

---

### 2.3 【中】仅 RWA 首次质押时 users 表可能无行，推荐关系未写入 users

**现象**：  
- `handleRWAStakeEvent` 只写入 `stakes` 和 `rwa_stakes`，**不写 `users` 表**。  
- 随后 `bindReferralRelationship(user, referrer)` 执行 `UPDATE users SET referrer = ? WHERE address = ?`，若该 address 尚未在 `users` 中存在，则 **0 行被更新**，`users.referrer` 仍为空。

**后果**：  
仅做过 RWA 质押、从未做过 USDT 质押的用户，在 DB 中可能没有 `users.referrer`；后续若用 `users.referrer` 或依赖其构建的 `referral_relations` 做统计/奖励，会漏人或错人。

**建议**：  
在 `handleRWAStakeEvent` 中，对首次出现的 address 做一次 `users` 的 INSERT（或 UPSERT），至少写入 `address` 与 `referrer`，再调用 `bindReferralRelationship`；或让 `bindReferralRelationship` 在无 users 行时先 INSERT 再 UPDATE。

---

### 2.4 【中】RWA 质押无最低“100 USDT 等值”校验

**现象**：  
- 文档与前端文案写“最低 100 USDT 等值”，USDT 质押合约中有 `require(amount >= 100 * 10^6)`。  
- RWA 质押合约仅 `require(amount > 0)`，**无**按 RWA 价格换算成 100 USDT 等值的校验。

**后果**：  
用户可用极少 RWA（如 1 wei）完成一次 RWA 质押并绑定推荐人，从而“占位”推荐关系；后续该用户大额 USDT 质押时，推荐奖励会发给该推荐人。合规/风控上可能不符合“最低 100 USDT 等值”的设计。

**建议**：  
- 在合约中为 RWA 质押增加最低数量校验（需价格预言机或管理员设置最低 RWA 数量），或  
- 在前端至少按当前 RWA 价格换算并限制“等效 100 USDT”再允许发起质押，并在文档中说明“链上仅校验 RWA 数量，等效 100 USDT 由前端/策略保证”。

## 三、不合理与体验问题

### 3.1 提现文案与合约逻辑不完全一致

**现象**：  
- 知识库/文案写“5% 手续费、24 小时冷却”。  
- 合约 `withdraw(amount, chooseStRWA)` 确为 5% 费 + 24h 冷却；但在“提 U”模式下，合约再对 **扣费后金额** 做 70% 给用户、30% 销毁，即用户实际到手约为 **amount × 0.95 × 0.7 ≈ 66.5%**。  
- 前端 `rwa-withdraw-card.tsx` 写“70% for withdrawU”“30% burn”，未明确说明这是“扣 5% 费之后的 70/30”，容易让人误以为总提现额的 70%。

**建议**：  
在提现卡或知识库中明确写清：先扣 5% 手续费，剩余部分再按“提 U：70% 到账 / 30% 销毁”或“持 RWA：120% 转 stRWA”计算。

---

### 3.2 紧急提现用 RWA 退还但本金是 USDT

**现象**：  
`emergencyWithdraw()` 中：  
- `refundAmount = user.totalStaked / 2`（USDT 质押额的 50%，数值为 18 位精度）。  
- 实际执行 `rwaToken.safeTransfer(msg.sender, finalRefund)`，即用 **RWA 代币** 退还。

**后果**：  
若 1 RWA ≠ 1 USDT，用户拿到的 RWA 数量与“50% USDT 本金”的价值可能严重偏离；合约注释也写明“In production, this should use price oracle for conversion”。当前无预言机则存在价值偏差甚至合约 RWA 余额不足的风险。

**建议**：  
- 短期：在界面和文档中明确说明“紧急提现退还的是 RWA，数量按合约内公式计算，可能与 50% USDT 等值存在价差”。  
- 长期：引入价格预言机或约定换算规则，使退还数量与“50% USDT 等值”一致，或改为退还 USDT（若资金池支持）。

---

### 3.3 前端调试日志未关闭

**现象**：  
`stake-action-panel.tsx` 中有：  
`console.log('🔍 [StakeActionPanel] userStakeInfo:', ...)` 等。

**建议**：  
生产构建中移除或改为仅在开发环境输出，避免控制台泄露用户地址与推荐关系等信息。

---

### 3.4 提现流程中多笔交易未原子化

**现象**：  
当“可提现 = USDT 收益 + RWA 收益 + 灵活本金”时，前端会依次调用：  
`withdraw(usdtPart)`、`withdrawRWARewards(rwaPart)`、`withdrawFlexibleRWAPrincipal()` 等。  
若中间某一笔失败或用户只确认部分交易，会导致状态不一致（例如只提了部分、冷却已刷新）。

**建议**：  
- 在 UI 上明确说明“需多次签名，请全部完成”；  
- 若存在“必须一次性提完”的规则（如含灵活本金时），在文案和错误提示中强调，避免用户只执行了部分就离开。

---

## 四、已做得较好的点

1. **自我推荐防护**：合约中 `referrer != msg.sender`，无法把自己设为推荐人。  
2. **重复处理防护**：`processedStakes[stakeId]`、EventMonitor 的 tx_hash 幂等，防止重复发奖。  
3. **推荐奖励多级上限**：个人累计 ≤ 3× 质押、单笔 ≤ 50%、全局 ≤ 50%、软着陆等，合约与 RewardEngine 均有体现。  
4. **12 块确认延迟**：EventMonitor 再处理事件，降低分叉导致错误入账的风险。  
5. **前端推荐人展示**：已绑定推荐人时输入框清空并禁止修改，避免误填。

## 五、修复优先级建议

| 优先级 | 项目 | 建议动作 |
|--------|------|----------|
| P0 | RWA 收益无法提现 | 确认部署合约是否含 withdrawRWARewards；若无则补合约实现并部署/升级。 |
| P0 | 推荐人链上与 DB 不一致 | 统一“一人一推荐人”或后端按每笔质押的 referrer 算奖并维护关系。 |
| P1 | 仅 RWA 质押用户未写入 users.referrer | RWA 事件处理时保证 users 有行并正确写 referrer。 |
| P1 | RWA 最低 100 USDT 等值 | 合约或前端加强校验并与文档一致。 |
| P2 | 紧急提现价值偏差 | 文档/界面说明 + 长期预言机或规则。 |
| P2 | 提现说明 70/30 | 文案写清“扣 5% 后 70/30”。 |
| P3 | console.log、多笔提现说明 | 去掉生产日志、补充多笔提现说明。 |

## 六、小结

- **逻辑主线**：质押（USDT/RWA）→ 事件监听 → DB 与推荐关系 → 奖励计算 → 合约写 usdtRewards/rwaPending；用户侧提现 RWA 收益、灵活/锁仓本金、USDT 推荐奖励。  
- **最大风险**：推荐人链上与 DB 不一致导致奖励发错人；RWA 质押收益若缺少链上提现接口则无法提现。  
- **用户层**：需在文档和界面上补足“提现比例与顺序”“紧急提现为 RWA 及价差”“多笔签名”等说明，并统一最低门槛与推荐人语义。

完成上述 P0/P1 项后，再配合合约与后端的一致性校验（含单测/集成测试），可显著降低用户资金与奖励错误风险。
